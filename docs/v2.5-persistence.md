# V2.5 persistence foundation

This document records the implemented database contract for spec v2.5
§7A.1, §7A.8, §11.10, §11.10.1, and §15.8. It does not describe runtime or UI
integration; those remain deferred.

## Stored records

- `hypothesis_master` is the global H1–H9 identifier set. It contains no
  student data.
- `hypothesis_evidence` is append-only, tenant-owned evidence. It records the
  student, branch, hypothesis, evidence key, kanji, weight, source quality,
  observation time, and creation time. Inserting evidence has no database
  trigger or function that changes confirmed state.
- `source_kind` is the persisted administration-context label from the
  §11.4.1 source-factor table: `probe_item`, `targeted_practice`,
  `manual_with_response`, `incidental_item`, `home_unsupervised`, or
  `manual_without_response`. It is distinct from item format and content
  origin. Existing results retain NULL (unknown) provenance and are not used
  for H1 evidence.
- `student_hypothesis_state` stores one confirmed five-state value per
  `(student, hypothesis)`. Every new row starts at `undetected`.
- `state_recommendation` stores a non-empty, legible JSON basis and one pending
  proposal at most per `(student, hypothesis)`. Pending records never expire.
- `hypothesis_state_audit` and `state_recommendation_audit` are append-only.
  They attribute every approval or rejection and preserve the approved state
  transition and recommendation basis.

## Human authority and mutation boundary

Direct changes to `student_hypothesis_state.status` and direct resolution of a
recommendation are rejected by database triggers. The only implemented state
transition operation is `resolve_state_recommendation`, and execute permission
is revoked from `PUBLIC`. Deployment must grant it only to the application
role used by the explicit recommendation-approval handler.

The function accepts only `approved` or `rejected`, locks the pending
recommendation and current state, verifies the active actor belongs to the
authenticated `app.current_org` tenant, requires the actor to match
`app.current_user`, and requires instructors to be assigned to the student.
Approval changes state once and appends both audit records. Rejection leaves
state unchanged and appends an attributable resolution audit record.

No evidence accumulator, H1–H9 classifier, report path, timeout, or database
default calls this function. Recommendation generation and superseding are
not implemented in this PR. Proposal fields are immutable until that later
workflow supplies an audited superseding operation.

## Tenant boundary

Every student-owned record carries `org_id`, `branch_id`, and `student_id`.
Composite foreign keys bind those values to the same student row; resolver and
approver identities are similarly bound to the recommendation organisation.
All tenant tables enable and force RLS, and use `current_org_id()` in both
visibility and write checks. `FORCE ROW LEVEL SECURITY` prevents a table-owner
application role from using PostgreSQL's owner bypass. CI uses both an ordinary
role and an actual table-owner role to prove cross-tenant reads are filtered
and cross-tenant writes are rejected.

Both audit tables reject direct inserts, including from a role that has table
`INSERT` permission. The security-definer resolution function opens a
recommendation-specific, transaction-local insert capability only while it
appends the corresponding audit records, then clears it.

## H8 admission boundary

This migration creates no curriculum-admission table, trigger, or publishing
path. H8 candidates remain in the existing versioned snapshot with
`decision: pending`, `reviewer: null`, and `reviewed_at: null`; schema tests
assert that unreviewed material remains unadmitted. A later, separately
reviewed curriculum workflow must implement §6.7 human pruning.

## Known specification gap

The repository does not contain the original full §7A.1–§7A.4 base document;
`docs/CURRENT.md` already records this. Accordingly, this migration does not
invent detailed evidence payload, threshold, accumulator, or candidate-
hypothesis schemas beyond fields expressly needed by the v2.5 amendment.
